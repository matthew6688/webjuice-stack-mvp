# Handoff Schema V2 · Proposal

Status: **proposal** · written 2026-05-18 after finding multiple slug/path mismatches in V1 handoff.

## Why this is needed

V1 handoff has authoritative data scattered across files with no enforced cross-references:

```
handoff/od-package/
├── facts.json
├── structure/
│   ├── page-map.json              ← page slugs + h1 + roles
│   ├── section-bindings.json      ← what blocks per page  (OPTIONAL · sometimes missing)
│   ├── header.json                ← nav links
│   ├── footer.json                ← footer columns
│   ├── cta-system.json
│   └── page-sections.json
├── content/
│   ├── services.json              ← page_slug PER SERVICE (often mismatched with page-map)
│   ├── faq.json
│   ├── hero-copy.json             ← candidates array (composer picks [0])
│   ├── about.md
│   ├── team.json                  ← generated by pl:gen-narrative
│   ├── timeline.json              ← generated by pl:gen-narrative
│   ├── case-studies.json          ← generated by pl:gen-narrative
│   └── reviews.json
├── brand/
│   ├── brand-spec.json
│   └── logo-light.svg
├── shared/
│   ├── header.html                ← pre-baked (we now regenerate)
│   ├── footer.html                ← pre-baked (we now regenerate)
│   └── shared.css
└── assets/
    ├── hero-roof.jpg
    └── work/
```

**Bugs caused by V1 fragmentation** (real, found this session):

1. `services.json[0].page_slug` = `/roof-replacement` but `page-map.pages[3].slug` = `/services/roof-replacement` → footer links all 404
2. `shared/header.html` baked with H1 strings as nav labels ("Colorbond Roof Replacement in Ballarat")
3. `shared/header.html` baked with `href="/about"` root-absolute paths that break under sub-path serving
4. `section-bindings.json` missing for 2/3 customers (VIP, Mark) → composer falls back to DEFAULT_BLOCKS
5. `hero-copy.json[0]` is whatever order the upstream wrote — for vicwest it's the PAS storm-damage angle, applied to every page until per-role override
6. No validation that `section-bindings.json[N].blocks[M].type` matches a module that actually exists
7. No validation that asset references (`assets/hero-roof.jpg`) actually exist on disk

## Schema rules (enforced by `pl:validate-handoff`)

1. **Page slugs are unique** within `pages[]`
2. **All `*_ref` paths resolve** — `service_ref` → `services[].id`, `page_ref` → `pages[].id`, `photo_ref` → `assets.work[]` or `assets.team[]`
3. **All `blocks[].type` values** are loadable from the niche module library (currently 27 types)
4. **All `blocks[].variant`** values, when present, correspond to a real `.html` file in `modules/<type>/<variant>.html`
5. **Asset files exist** — every path under `brand.*` and `assets.*` is on disk
6. **Service-detail pages have a `service_ref`** that points to a real service
7. **No bare HTML files** in handoff — `shared/header.html` / `shared/footer.html` are now COMPOSER OUTPUTS, not inputs
8. **No legacy duplicates** — `structure/{header.json, footer.json, cta-system.json, page-sections.json}` deprecated

## Composer changes when V2 is in

- Single load of `v2-spec.json`
- Page-map / section-bindings / services / hero-copy / facts all come from one tree
- No `pl:reconcile-handoff` needed (consistency enforced at write time)
- No `pl:rebuild-header-footer` needed (header/footer generated from `header` / `footer` blocks in spec at compose time)
- No `services.json` page_slug drift possible (services are referenced by ID, pages own their slugs)

## Migration plan

1. Build the schema validator `pl:validate-handoff` (uses `ajv` JSON Schema validator)
2. Build `pl:migrate-handoff-v1-to-v2` script that:
   - Reads facts/services/page-map/etc.
   - Reconciles slug mismatches (existing `pl:reconcile-handoff` logic, plus more)
   - Drops shared/header.html and shared/footer.html (composer generates)
   - Writes one `v2-spec.json`
3. Run on 3 current customers · verify composer accepts V2 input
4. Update composer to read V2 spec directly when available, fall back to V1 when not
5. Update all upstream generators (B0/B1/B2 etc.) to produce V2 spec directly

## Why one file (not the same multi-file layout with stricter rules)

- **Atomic**: validate the whole consistency in one pass, no partial writes
- **Diffable**: one JSON file in PR is easier to review than 10 files
- **Composable**: future niches (electrician/plumber) inherit the same schema with niche-specific extensions
- **Tooling-friendly**: JSON Schema gives autocomplete in editors + CI validation
- **Failure-loud**: corruption shows up as a schema error, not a 404 in production
